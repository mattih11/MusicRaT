# MusicRaT Application Designer

Early browser-based editor for pre-launch MusicRaT applications. It consumes
generated CommRaT module descriptors, displays stable MusicRaT physical and
virtual ports, validates typed connections, and exports native CommRaT
application JSON.

This tool does not define a second graph format. Stable port IDs are editor-side
references resolved to descriptor positions during export.

## Unified graph

**Graph** combines audio/note routing, parameter bindings, semantic actions,
and feedback. Modules are green, UI widgets blue, hardware controls amber, and
implementation modules muted purple. **Hardware** remains the physical-placement
editor and **UI** remains the screen-layout editor; their controls appear in the
same graph automatically.

- Drag module audio/note outputs to compatible physical inputs.
- Drag a UI or hardware control to a module's named parameter or action.
- Drag parameter **state** outputs or channel-specific telemetry to feedback
  inputs. A UI parameter control gets authoritative feedback automatically when
  the target publishes parameter state. Hardware feedback follows its control
  binding; ambiguous bindings require selecting the destination in the inspector.
- Select a control cable to edit its mode, pickup, curve, transform, or priority
  in the inspector. Action cables expose quantization and ramp timing.
- Select a cable and press Delete/Backspace (or use **Disconnect cable**) to
  remove it. Feedback can be disconnected independently of a UI control cable.

Only writable automatable parameters with a typed parameter-event input are
connectable. Startup-only parameters stay in the module inspector rather than
pretending to support live control. Graph and UI target selectors use the same
validated endpoint catalogs. Positions and stable-ID bindings survive draft
save/open and launch export/import.

Adapters such as ControlMapper, ActionMapper, ParameterStateUiAdapter,
ControlFeedbackRouter, LVGL sinks and widget-update mergers are generated by the
existing launch compiler, not manually inserted by users. **Show implementation
modules** exposes both configured implementation modules and a read-only preview
of the actual generated modules and runtime routes. Generated parameters can be
inspected but are never stored as additional editable project modules. Preview
compilation errors are shown explicitly; missing installed descriptors are
identified and use positional port labels.

Existing compiler limits still apply: a hardware device needs a configured
compatible adapter, telemetry adapters support the implemented payload/property
combinations, and multiple control owners feeding one parameter-event input
require a control bus (not currently generated). Launch-readiness errors appear
in the status bar and export rejects unsupported graphs.

## Keyboard note routing

Add a display in **Hardware**, then place a **Keyboard** widget on that display
in **UI**. The keyboard also appears as an LVGL note source in **Graph**.
Drag its **Note events** handle to a synth's note input, for example the
ThreeOscillator or WavetableOscillator. One keyboard can feed multiple synths.
Select a cable and press Delete to disconnect; move the keyboard node to arrange
the graph. Its position and cables survive Save/Open and application export.
Remove the widget itself in UI, not by deleting its graph node.

The keyboard's **Note targets** selector in UI edits the same routes. Both
surfaces accept only note-domain synchronized inputs carrying `NoteEventBlock`,
and reject inputs already fed by another source. Existing projects using the
older single-target selector remain supported. Keyboard routes reference stable
module and port IDs; export resolves them to the generated LVGL adapter's note
output and the target's exact `synced_inputs` position. The keyboard graph node
is a view of the UI widget, not another launchable module.

All keyboards on one display share that display's note stream. Independent
keyboard streams require separate displays/adapters.

## Development

### Live three-oscillator desktop project

After building the SDL-enabled modules, generate an editable Designer project,
an LVGL manifest, and its compiled launch configuration:

```bash
cd tools/application-designer
CHOKIDAR_USEPOLLING=true ./node_modules/.bin/vite-node \
  scripts/create-three-oscillator-demo.ts ../../build-lvgl-sdl-validation
cd ../..
./build-lvgl-sdl-validation/musicrat_launcher \
  ./build-lvgl-sdl-validation/three-oscillator-live/ThreeOscillatorLive.json
```

A CoreRaT TCP router must already be available. Do not start a second router
if one is running. Import `ThreeOscillatorLive.musicrat.json` from the generated
directory to edit the project in the unified Graph and UI layout.

The 1600x1000 SDL window has a keyboard with octave selection and 23
bidirectional sound controls, including waveform choices, oscillator tuning
and levels, amplitude ADSR, filter mode/cutoff/resonance, and filter ADSR.
Sample rate stays fixed at startup. Envelope settings apply to subsequent
notes; changing them does not restart held envelopes.

Generated LVGL producers precede subscribing control mappers at launch.
Starting the mapper first can leave the control subscription inactive while
state feedback continues, making every widget revert to its old value.
Feedback must also not overwrite a slider/fader/knob while it is being dragged.
Choice controls emit their actual choice values and receive typed choice
feedback, rather than treating enum values as normalized continuous controls.

Requires Node.js 18 or newer.

Audio file player observations are available in the shared Graph/UI target
catalog. Connect elapsed/remaining time to text, track position to a continuous
widget, playing/ready/looping to a toggle/button, and worker/error state to a
choice widget. Strict export generates `MusicRaTPlaybackStatusUiAdapter` and
merges its updates with other observations for the same display. Generated
adapters stay hidden in the default module picker. Unavailable values visibly
disable widgets until a valid snapshot arrives. This does not yet add waveform,
browser, load/seek gestures, or calibrated audible-time interpolation.

```bash
npm install
npm test
npm run dev
```

Run the local descriptor catalog in a second terminal:

```bash
MUSICRAT_MODULE_PATH=/path/to/modules \
MUSICRAT_PROJECT_DIR=/path/to/projects \
npm run host
```

Vite proxies `/api/catalog` to the host on port 4174. The host searches
`MUSICRAT_MODULE_PATH`, the XDG user/system data directories, and the default
MusicRaT installation data directory in that order. A production build is also
served directly by the host at `http://127.0.0.1:4174`.

Without the host, the browser uses an explicit demonstration catalog. Project
files and descriptors can also be loaded manually. With the host, projects are
listed, loaded, and saved atomically with revision checks. The default project
directory is `$XDG_CONFIG_HOME/musicrat/applications`, falling back to
`~/.config/musicrat/applications`; `MUSICRAT_PROJECT_DIR` or
`--project-dir=<path>` overrides it. The designer does not currently own
application processes. A future integration may hand a validated saved revision
to an external launcher/controller once runtime ownership is defined.
